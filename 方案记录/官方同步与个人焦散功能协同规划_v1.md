## 2. 分支和目录职责

采用“官方基线、个人功能、同步分支”三层结构：

| 名称 | 职责 | 规则 |
| --- | --- | --- |
| `upstream` | 跟踪 Blender 官方仓库 | 只读跟踪，不在此分支开发个人功能 |
| `main` | 可发布的整合分支 | 只接收已验证的官方同步和个人功能 |
| `feature/caustics-*` | 表面焦散、SPPM、引导采样等单项功能 | 一个分支只解决一个主题 |
| `feature/volumetric-caustics-*` | 体积焦散和丁达尔效应 | 先完成 CPU 基线，再接 GPU |
| `feature/vulkan-*` | Vulkan 后端研究与实现 | 与渲染估计器改动分开推进 |
| `sync/blender-*` | 一次官方更新的临时整合分支 | 完成冲突处理和验证后合并回 `main` |

建议为官方仓库增加远程名 `upstream`，地址以 Blender 官方代码仓库为准：
`https://projects.blender.org/blender/blender`。

## 3. 个人下游分支的官方补丁同步流程

本仓库是个人下游分支。Blender 官方仓库只作为补丁、修复和版本更新来源，不向官方提交本仓库的个人功能。

每次同步都按同一顺序执行：

1. 检查工作区干净状态，给当前 `main` 创建可恢复标签或分支。
2. 更新 `upstream` 远程引用，记录同步日期和目标 commit。
3. 从当前 `main` 创建 `sync/blender-日期或版本`。
4. 使用官方推荐的 rebase/pull 流程或明确的 merge 提交整合上游；整个同步提交不夹带个人功能。
5. 按文件分组解决冲突，优先保留官方修复，再重新接入个人代码的最小适配层。
6. 完成 CPU 编译、CUDA/OptiX 内核生成、Blender 启动和设备发现检查。
7. 运行焦散、体积雾/丁达尔和普通 Cycles 对照场景。
8. 记录上游 commit、冲突文件、决议、构建配置、测试结果和已知限制。
9. 将同步分支合并回 `main`，再继续个人功能分支的开发。

### 构建产物一致性注意事项

- 任何 C/C++、CMake、Cycles 内核或着色器改动，都必须在源码验证前完成对应配置的增量或完整构建；只修改源码文件不能代表运行版本已经更新。
- 构建成功后必须执行安装步骤，将新产物覆盖到唯一测试目录；测试不得混用构建目录、安装目录和旧便携版目录中的 `blender.exe`。
- 启动测试前记录实际启动的可执行文件完整路径，并核对文件时间戳、大小或 SHA-256 与本次构建产物一致；发现路径或时间不一致时，停止结果判断并先修正运行布局。
- 涉及 CUDA、OptiX、Vulkan 或其他设备内核时，除主程序外还要确认对应内核目标已生成并随安装目录更新。
- 构建、安装、启动和测试日志必须作为同一变更的验证记录；没有新构建产物的测试只能算源码静态检查，不能用于判断运行效果或性能变化。

官方 Git 文档提供了 rebase、合并和冲突处理的操作依据；本流程将这些操作固定到个人下游分支管理中。

## 4. 个人功能的进入规则

- 优先新增独立模块、独立数据结构和独立 pass，减少对通用路径的直接改写。
- 功能开关默认关闭，关闭时保持官方 Blender 的现有结果和性能路径。
- 先建立 CPU 参考实现，再移植 CUDA/OptiX；Vulkan 作为单独后端接入。
- 每项功能都要有回退路径、容量上限、取消处理和显存预算。
- 不把本机 CUDA、OptiX、Visual Studio 或 `lib/` 绝对路径写入源码。
- 不修改自动生成文件和第三方源码，除非构建系统明确要求且许可信息已核对。
- 个人功能提交保持小而完整，每个提交都应能单独编译、测试和回滚。

### 方案选型和 API 适配原则

- 新功能和视觉效果优先采用已有验证、可行且成熟的最佳方案；先查阅当前 Blender 源码、官方文档、官方仓库或相应方案的原始资料，再决定实现路径。
- 禁止凭空假设算法、接口或效果行为。缺少可验证依据时，先建立最小验证场景或原型，确认后再进入正式实现。
- Python API、RNA 和节点接口必须以当前构建版本的实际查询结果和最新官方 API 文档为准。当前 Blender 版本更新很快，历史印象和旧版示例不能作为适配依据。
- API 适配前先确认属性、枚举、节点接口和数据读取方式；适配后必须在当前构建版 Blender 中执行对应脚本验证。

### 官方玻璃色散合并规划（P4）

官方可复用基线已经确认：Blender 官方提交 `f15daf81bf7c0729761ca81fc0ad0ee07b602bc5`，标题为
`Cycles: Add dispersion to Principled BSDF`，已进入官方 `main`，对应 Blender 5.3 Alpha 开发阶段。
提交地址：`https://github.com/blender/blender/commit/f15daf81bf7c0729761ca81fc0ad0ee07b602bc5`。

官方实现范围包括：

- Principled BSDF 的 `Transmission Dispersion Scale` 和 `Transmission Dispersion Abbe Number` 输入。
- 基于 Cauchy 经验公式的波长相关 IOR。
- 光谱波长采样、RGB 转换、SVM、OSL、CPU/GPU 内核和 MNEE 适配。
- shader graph、节点 RNA、版本迁移和官方回归资源。

当前分支的合并策略：

1. 以官方提交涉及的 Cycles 文件为边界，逐文件移植；保留当前分支的焦散、体积焦散和 OptiX 改动。
2. 先让普通 Cycles Principled BSDF 路径获得官方色散，再接入表面焦散的材质分类和光子发射。
3. 色散材质沿光子路径传递波长或等效光谱状态；光子能量、折射 IOR、光子束和接收端使用同一套波长规则。
4. 体积焦散沿用同一波长状态计算介质内折射与散射，体积吸收和散射系数按波长转换，避免表面色散与丁达尔光束颜色分离。
5. OptiX、CUDA 和 CPU 共享同一数据布局与公式；设备不支持光谱路径时明确回退到已验证的 RGB/原生路径。
6. 检测到色散材质时关闭该材质的自定义 RGB 光子替代路径，避免官方路径和光子路径重复计数；无色散材质继续使用现有高性能光子路径。

实施阶段和放行条件：

| 阶段 | 目标 | 放行条件 |
| --- | --- | --- |
| P4-A | 移植官方 Principled 色散字段、节点、SVM/OSL 和版本兼容 | 当前 Blender 可创建/保存字段，普通 CPU/GPU 渲染出现稳定色散 |
| P4-B | 表面焦散兼容 | 棱镜、玻璃球、玻璃平面色散位置正确；色散关闭时与现有结果一致 |
| P4-C | 体积焦散兼容 | 玻璃入射到雾体后出现连续色谱光束；吸收、散射和能量随波长变化合理 |
| P4-D | OptiX/CUDA 性能与回退 | OptiX 与 CPU 参考图形状一致；不支持光谱的设备有明确回退且不崩溃 |

验收场景固定为：白光棱镜、玻璃球聚焦、玻璃容器加纹理密度体积、彩色体积雾、色散开关 A/B、不同 Abbe 数和 Dispersion Scale 对照。

已知技术边界：当前光子缓存使用 RGB `float3` 能量，完整色散需要扩展光子发射、折射、光子束、缓存和 gather 数据；只移植官方 Principled 节点可以得到普通路径色散，无法自动保证自定义表面焦散和体积焦散一致。因此 P4 必须拆分提交、逐阶段编译和逐阶段回归，禁止一次性覆盖当前焦散实现。

### 官方性能与质量基线

个人焦散功能要达到可长期使用的综合体验，必须同时满足画面质量、物理可信度、交互流畅度和资源可控性。以下原则来自当前 Blender/Cycles 源码中的稳定做法，作为各功能阶段的共同门槛：

- **条件化计算**：沿用官方 MNEE/Shadow Caustics 的思路，只在光源、焦散施加体和接收体条件成立时创建相关工作；焦散关闭或场景没有有效焦散链时，普通 Cycles 路径保持原有工作量。
- **优先减少无效样本**：沿用 Light Tree、光源采样阈值、材质/物体筛选和光子目标筛选，优先提升 Useful Photons/s 与有效 gather 比例，再增加总光子数。
- **渐进与可取消**：光子批次、SPPM gather 和后端任务必须增量发布，支持取消、场景更新和容量上限；主线程和视口绘制线程不能等待整批 GPU 工作完成。
- **导航优先**：视口识别导航/变换状态，导航期间暂停新一代高成本焦散追踪，只复用已经完成的稳定结果；相机重置只使图像累积失效，不同步销毁与重建场景级光子数据。
- **官方采样策略优先**：交互渲染沿用蓝噪声首样本或等效的低频噪声策略，最终渲染沿用完整蓝噪声/当前官方采样模式；采样模式的改变必须以当前源码和构建版行为为准。
- **估计器与显示层分离**：自适应采样必须依据 Combined 等官方统一统计口径，降噪、平滑和 DLSS 只能作用于显示结果，不能修改光子能量、半径更新或 Guiding 反馈。
- **设备能力显式处理**：按 `DeviceInfo` 能力矩阵决定 MNEE、路径引导、OptiX、CUDA、Vulkan 和降噪器的可用路径；缺少能力时记录原因并回退到已验证后端，禁止静默改变物理语义。
- **资源预算可观测**：记录 GPU 时间、CPU 时间、显存峰值、光子吞吐、有效光子率、取消延迟和视口帧间隔；任何质量提升都要与资源代价一起验收。
- **结果可比较**：Viewport 与 Final 共用同一物理估计器、PDF、材质路径、能量归一化和半径规则。两者允许样本数不同，焦散位置、形状、相对亮度和收敛方向必须一致。

性能优化的放行顺序固定为：

```text
先保证物理正确和结果可回归
→ 再减少无效光子与无效 gather
→ 再优化 GPU/CPU 并发和内存
→ 最后加入显示层加速
```

任何优化若造成导航卡顿、后台渲染阻塞、显存无界增长、能量漂移或 Viewport/Final 结果分叉，都必须回退到上一个已验证版本。

### 优先级

| 优先级 | 功能或修复规划 | 前置验收重点 |
| --- | --- | --- |
| P1 | 表面焦散半径/光子差分稳定性 | 半径稳定、边缘清晰度、动画一致性、能量稳定性；有效光子率提升且显存和帧间隔受控 |
| P2 | 丁达尔体积焦散 | 均匀体积、单次散射、CPU/CUDA/OptiX 一致性；体积光子与表面光子分离统计，避免重复计数 |
| P3 | Vulkan 光子后端 | 与 CPU 参考实现和既有 GPU 后端的结果对照；能力检测、资源回收、取消和跨后端回退完整 |
| P4 | 玻璃色散 | 光谱分离正确性、能量守恒和现有玻璃材质兼容性；材质评估成本、噪声和显存增量有记录 |
| P5 | 视口 DLSS | 视口稳定性、延迟、清晰度和与焦散结果的兼容性；只加速显示层，导航和最终渲染估计器保持一致 |

## 5. 个人仓库提交规范

提交前缀建议固定为：

- `Sync:` 官方上游同步和冲突适配
- `Caustics:` 表面焦散、光子图和 SPPM
- `Volumetrics:` 体积焦散、雾和丁达尔效应
- `Vulkan:` Vulkan 后端
- `Build:` 构建系统和平台配置
- `Tests:` 回归场景和验证工具

下列内容保持独立提交：

- 官方同步与个人功能
- 功能实现与格式化/大范围重构
- CPU 参考实现与 GPU 移植
- 算法变更与 UI/参数变更

每个功能提交说明至少包含：问题、方案、替代方案、限制、兼容性、测试场景和性能变化。较大的设计先形成方案记录，再进入实现。

## 6. 验证矩阵和放行条件

### 每次官方同步必测

- CPU 配置编译。
- CUDA 内核生成，目标包含 RTX 3080 的 `sm_86`。
- OptiX PTX 生成。
- Blender 启动、CUDA/OptiX 设备发现和最小后台渲染。
- 普通玻璃/水面场景结果与同步前对照。

### 触及焦散或体积路径时追加

- 单玻璃平面 + 均匀雾盒 + 太阳光。
- 水面 + 水下雾 + 接收面。
- 聚光灯 + 玻璃棱镜 + 窄体积通道。
- `Volume Caustics` 开关前后对照。
- `sigma_s = 0` 时体积焦散为零。
- 光源强度翻倍时平均能量翻倍。
- 光子数增加后噪声下降，平均能量稳定。
- CPU、CUDA、OptiX 的焦散位置、能量和收敛方向一致。

### 放行条件

- 官方修复可复现地解决目标问题。
- 个人功能关闭时无可见回归。
- 个人功能开启时有独立结果和性能记录。
- 冲突决议、测试环境和已知限制已经写入提交说明。
- 任一后端失败时能明确回退到可用路径。

## 7. 发布和 GPL 注意事项

- 源码仓库提交源码、方案、必要的构建脚本和可复现测试场景。
- 编译版通过 GitHub Release 发布，附 commit、编译器、CUDA/OptiX 版本、已验证 GPU、已知限制和 SHA-256。
- 不发布 `lib/`、`build/`、CMake 缓存、SDK 安装器和本机临时文件。
- 保留仓库中的 `COPYING`、`NOTICE`、`AUTHORS` 及第三方许可文件。
- 发布可执行文件时提供对应源码获取方式和构建信息，第三方组件继续遵守各自许可。
- 发布前检查个人仓库地址、标签、源码 commit、二进制包内容和哈希值一致。

## 8. 每次开发前后的检查清单

### 开始前

- 确认当前分支、上游基线和远程地址。
- 确认是否需要源码快速备份；新增功能或大范围改动先创建备份点。
- 确认改动属于哪个单一主题，避免把同步、功能和重构混在一起。
- 确认目标后端、测试场景和放行条件。
- 确认本次改动需要构建的目标、安装目录和实际启动路径。

### 合并前

- 查看冲突是否只涉及预期文件。
- 检查是否误加入 `lib/`、`build/` 或本机路径。
- 完成对应验证矩阵，保存日志和输出图。
- 记录性能、显存、图像差异和已知限制。
- 核对测试进程使用的 `blender.exe` 与本次构建、安装产物一致，避免用旧程序得出结论。

### 发布前

- 确认源码和二进制来自同一 commit。
- 确认官方修复和个人功能可以分别追溯、分别回滚。
- 确认 GPL、NOTICE、AUTHORS 和第三方许可文件完整。
- 确认 Release 压缩包内容、SHA-256 和下载说明。

## 9. 当前执行顺序

1. 确认并固定 `upstream` 地址，保留当前 `main` 作为个人发布基线。
2. 为官方同步建立首个 `sync/blender-*` 分支，先完成一次无个人功能的同步演练。
3. 按 P1 到 P5 的顺序推进表面焦散稳定性、丁达尔体积焦散、Vulkan 光子后端、玻璃色散和视口 DLSS。
4. 每次官方同步后重新跑已完成阶段的回归矩阵，再继续个人功能开发。
5. 达到放行条件后发布个人仓库的源码标签和对应的 GitHub Release。

核心平衡原则：官方同步保持独立、个人功能保持可开关、验证结果保持可比较、每次合并保持可回退。
