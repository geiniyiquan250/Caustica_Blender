# 个人焦散开发踩坑日志

本日志记录已经发生并影响过判断、构建或发布的事故。每次新增功能或同步官方补丁前后都要查阅。

## 2026-09-06：源码已更新，运行时仍加载旧 CUDA 内核

- 现象：源码和 `blender.exe` 已重新安装，但 RTX 3080 上的体积光束遮挡问题没有变化。
- 根因：OptiX 普通着色仍依赖 CUDA 公共内核；安装目录的 `kernel_sm_86.cubin.zst` 仍是旧文件，运行日志明确显示加载旧内核。
- 处理：启用 `WITH_CYCLES_CUDA_BINARIES=ON`，只构建 `sm_86`，重新执行 `ninja install`，核对构建目录与安装目录的 SHA-256 一致。
- 以后必须：涉及 Cycles 内核、着色器或数据布局的改动，必须同时检查对应 CUDA `cubin/ptx` 时间戳、大小和哈希；OptiX 测试必须保存“实际加载内核”日志。

## 2026-09-06：局部渲染裁剪区域没有覆盖相机前玻璃

- 现象：加玻璃和不加玻璃的对照图几乎没有差异，误以为玻璃后的体积查询失效。
- 根因：测试文件启用了 Render Border，裁剪区域在画面上方，而相机前玻璃位于画面下方。
- 处理：诊断渲染关闭 `render.use_border`，再做完整画面对照。
- 以后必须：视觉对照前记录并确认分辨率、Border、相机、物体隐藏状态和输出路径；局部渲染不能证明未覆盖区域的行为。

## 2026-08 至 2026-09：源码修复后没有重新构建

- 现象：恢复或修改 A/B 逻辑后，测试效果完全不变。
- 根因：只改了源码，没有生成新的 `blender.exe` 和设备内核，测试实际运行旧程序。
- 以后必须：源码改动、配置、构建、安装、实际启动路径必须作为一个闭环；没有新产物的结果只能算静态检查，不能作为效果或性能结论。

## 2026-08 至 2026-09：多个 Blender、构建目录和安装目录混用

- 现象：同一个 `.blend` 在“原版”和个人版本上表现不同，难以判断差异来自源码还是运行文件。
- 根因：同时存在作者编译版、旧个人版、构建目录中的程序和安装目录中的程序，启动路径没有固定。
- 以后必须：只保留一个用于验收的安装目录；每次测试记录 `blender.exe` 完整路径、文件时间戳、构建 commit 和内核目录。

## 2026-08 至 2026-09：Debug/非完整 Release 导致视口严重卡顿

- 现象：加入 P0 或切换编译器后，近距离导航画面不刷新、采样延迟明显增加。
- 根因：使用了不匹配的构建配置、旧内核或未完成的 Release 优化，不能与作者的完整 Release 版本直接比较。
- 处理：当前基线固定为 ClangCL + `CMAKE_BUILD_TYPE=Release`，关闭 CUDA 架构以外的无关目标，使用同一安装目录验证。
- 以后必须：发布候选版禁止带断言、Sanitizer 或低优化配置；构建日志要确认 `Release`、编译器和目标架构。

## 2026-08 至 2026-09：P0 物理闭环优化造成视口负面性能

- 现象：开启 P0 后视口导航卡顿，肉眼没有看到足以抵消性能代价的效果提升。
- 处理：P0 已回退并从当前优化目标移除。
- 以后必须：任何性能优化必须有开关、基准场景、帧间隔/取消延迟记录和前后图像对照；没有可见收益或能量验证时不进入正式基线。

## 2026-08 至 2026-09：体积焦散路径与标准体积流程重复或绕过

- 现象：玻璃外有体积光束，玻璃进入体积后消失；相机前玻璃还会屏蔽体积光束；混合体积纹理和简单体积节点结果不一致。
- 风险点：自定义 `volume_integrate_photon_beams()`、`film_write_volume_emission()`、体积堆栈、透射 visibility 和标准 `volume_integrate_homogeneous()`/ray marching 流程之间可能出现重复写回、错误吞吐量或错误介质状态。
- 以后必须：先用计数和日志确认“路径进入体积、BVH 查询、非零积分、最终写回”四个节点，再做集中修复；禁止只凭画面继续叠加条件。

## 2026-08 至 2026-09：能量、材质和几何验证不足

- 现象：平直玻璃板出现透镜状圆锥焦散，猴头出现菱形面片，透镜与玻璃板重叠出现异常白圈；提高光子数只能让面片更饱满，不能消除几何轮廓。
- 根因：光子半径、法线/差分、材质分类、色散、MNEE 和能量归一化没有用固定几何基准逐项隔离。
- 以后必须：固定平板、透镜、平滑猴头、重叠投射四类场景，分别检查形状、能量守恒、分辨率收敛和材质开关；参数上限调整不能替代算法验证。

## 2026-08 至 2026-09：OptiX 没有编译或设备内核不完整

- 现象：主程序能启动，但 OptiX 路径不可用，或 CPU 有效果而 GPU 没有。
- 以后必须：配置中显式确认 `WITH_CYCLES_DEVICE_OPTIX=ON`、CUDA 公共内核开启、OptiX PTX 已生成；启动日志必须出现 RTX 3080 OptiX 设备和对应内核加载记录。

## 2026-08 至 2026-09：构建运行时布局不完整

- 现象：ctest 能发现测试项，但 `blender.exe` 报并行配置错误或无法启动。
- 根因：只构建了二进制，没有执行安装，或运行目录缺少 `5.2`、`blender.crt`、`blender.shared`、Python 和 Cycles 内核布局。
- 以后必须：测试使用安装后的完整目录；构建完成必须执行 `ninja install`，再做启动、设备发现和最小渲染。

## 统一放行检查

1. 源码工作树、构建目录、安装目录和运行日志能对应到同一个 commit。
2. 只使用一个验收 `blender.exe`，记录完整路径和 SHA-256。
3. `Release` 配置无 Debug/Sanitizer；当前 RTX 3080 必须有新 `kernel_sm_86.cubin.zst`。
4. CUDA 公共内核和 OptiX PTX 都已生成并安装；加载日志能证明测试确实使用新文件。
5. 完成 CPU 与 OptiX 的最小对照，关闭 Border、合成器和序列器对诊断的干扰。
6. 记录光子批次、体积光束段、BVH 节点、渲染时间、显存和取消状态。
7. 视觉效果、性能和物理能量结论必须来自新构建，不能引用旧程序测试结果。

## GPU 架构发布基线

- RTX 20 系列：`sm_75`
- RTX 30 系列：`sm_86`
- RTX 40 系列：`sm_89`
- RTX 50 系列：`sm_120`

发布包必须包含以上四个 CUDA 压缩内核和 OptiX PTX；只生成本机 `sm_86` 会让其他系列回退、运行时编译或无法使用，不能作为通用安装包。
